Boa noite pessoal, nós vamos começar aqui a discussão sobre o SBOK, que é o Software Engineering Body of Knowledge. Basicamente, o SBOK é um guia, um livro que prescreve a área da engenharia de software a partir de áreas de conhecimento. Então, de certa forma, este guia delimita a área de engenharia de software, em especial as áreas em que o engenheiro de software pode atuar. Atualmente, o SBOK está na edição 4, que está sendo construída. Na verdade, eu tenho a versão do CBOK versão 3, edição 3, impressa. Estou aguardando sair a versão 4 do guia para poder atualizar essa apresentação. Essa apresentação eu já vou me basear no SBOK versão 4, que está neste momento sendo confeccionado para ser disponibilizado para toda a comunidade.

Conforme eu comentei com vocês, o SBOK é dividido em áreas de conhecimento que vão desde processo de software, teste de software, qualidade de software, requisitos de software, segurança de software. Mas para a nossa disciplina em particular, nós estamos muito preocupados com a área de requisitos de software.

Fazendo uma pequena introdução aqui, quando nós falamos de requisitos de software, é importante delimitarmos duas perspectivas. A primeira perspectiva é aquela em que os requisitos são uma expressão daquilo que é necessário para um produto de software ou para um projeto de software, de forma a contribuir para a solução de um problema do mundo real. Uma outra perspectiva, um outro prisma para nós enxergarmos a questão de requisitos de software, são a partir das atividades necessárias para desenvolvimento e manutenção de requisitos de software do produto de software e para o projeto que vai construir esse software. Lembrando apenas que ambas perspectivas, tanto a perspectiva do projeto como do produto, são apresentados nessa área de conhecimento presente no SBOK.

Mais uma vez, parece que já está claro para todos os stakeholders que são envolvidos na área de engenharia de sistemas ou de engenharia de software a importância de requisitos para o sucesso de qualquer projeto de desenvolvimento de software. De outra forma, ou em outras palavras, se um time desenvolve requisitos de forma ruim, de forma mal feita, o projeto ou produto, ou até mesmo ambos, vão sofrer de vários problemas. O que acredito que seja bastante intuitivo: se você levanta requisitos de forma errada, o seu projeto vai ter custos adicionais, vai ter atrasos, podendo ser até cancelados, e produzir muito produto de software com o que nós chamamos de bugs ou defeitos.

Talvez uma pergunta que fique é: por que requisitos mal documentados? Por que se nós levantarmos documentos de requisitos de maneira errada ou mal feita, por que isso afeta um projeto? Basta vocês lembrarem que existe um efeito cascata, porque às vezes um determinado requisito de software vai levar a muitas decisões de design e implementação. Então, a partir do momento que você fez um levantamento errado de requisito, e lembrando que os designs e implementações desses requisitos são desdobramentos do requisito, os seus designs serão feitos de forma errada e o seu software será implementado de forma errada. E quanto mais tarde você identificar um problema, achar um bug, mais caro é consertar esse bug. Então, nós temos que ter muito cuidado nessa fase de documentação de requisitos para que aquilo que a gente esteja fazendo esteja, digamos assim, mais próximo possível daquilo que realmente é necessário para nossos clientes e para os nossos usuários. Ou, em outras palavras, determinar corretamente os requisitos é algo de alto valor para todas as pessoas que estejam envolvidas em um projeto de desenvolvimento de software.

Mais uma vez, lembrando: se nós não detectarmos o quanto antes e repararmos o quanto antes requisitos incorretos, ausentes ou ambíguos, isso vai produzir de forma em cascata um trabalho árduo para todos os envolvidos, inclusive podendo levar os seus projetos a um fracasso.

Basicamente, existem duas principais razões, problemas que nós nos deparamos quando a gente trabalha com documentação de requisitos de software. O primeiro é incompletude: é quando o requisito existe, mas o analista de requisitos, o engenheiro de requisitos, o product owner ou qualquer pessoa envolvida na sua empresa com a funcionalidade de capturar requisito não percebe a existência desse requisito e não documenta e não comunica esse requisito para os desenvolvedores. Então, o requisito existe mas não foi documentado. Quer dizer que o seu software não vai atender esse requisito e talvez ele seja essencial para o seu negócio. Um outro problema que acontece muito e é muito importante é a questão da ambiguidade. Ou seja, quando você comunica os requisitos para sua equipe de desenvolvimento de uma maneira que deixa certa ambiguidade no ar, e de forma que os próprios desenvolvedores interpretam aquele requisito de uma forma que não necessariamente é a forma correta, ele acaba produzindo, por exemplo, um software que não está de acordo com os requisitos que foram pré-estabelecidos.

Talvez um exemplo simples que você já tenha estudado na engenharia de software é quando vocês usam dois termos para referenciar o mesmo conceito. Imagina o sistema acadêmico: às vezes um requisito está especificando que o estudante deverá fazer tal coisa, talvez um outro requisito diz que o aluno deverá fazer tal coisa. Repare que um requisito define "estudante" e outro define "aluno". Se você passa isso para uma equipe de desenvolvimento, talvez para desenvolvedores independentes, pode ser que eles criem duas classes: a classe Aluno e a classe Estudante, quando na verdade você deveria ter uma classe apenas que representa aquele requisito. Ou seja, você tem ambiguidade no seu requisito, levando a interpretações conflitantes em determinados momentos pelo time de desenvolvimento.

Lembrando também que nós temos a questão de bugs, defeitos. Não vou entrar muito na terminologia nesse momento, embora ela seja muito importante, mas talvez uma forma de você enxergar que um defeito ou um bug nada mais é do que a implementação de um requisito que desvia da intenção original do seu requisito. Ou, em outras palavras, é a diferença que você observa entre o que o software deveria fazer e o que ele realmente faz. Essa diferença é um bug, ou seja, desviar do objetivo de um determinado requisito, fazendo com que o seu software não opere de acordo com as necessidades dos seus clientes.

Conforme falei com vocês, na área de engenharia de sistemas, documentação de requisitos é crucial. O modelo de ciclo de vida V Model, ou V Model como é pronunciado em inglês, ele é estritamente baseado em documentação, inclusive por questões de auditoria. Já na engenharia de software, não necessariamente é dessa forma. Os métodos ágeis, por exemplo, trabalham muito com o conceito de histórias de usuário para identificação de requisitos, e as histórias de usuários não são uma especificação de requisitos. Elas são, digamos assim, documentos menos formais que priorizam a comunicação entre time de desenvolvimento e clientes para desenvolvimento de um software de qualidade.

Entretanto, requisitos por si só são muito importantes, seja ele em engenharia de sistemas, engenharia de software, seja em métodos ágeis que é uma maneira menos formal de descrever esses requisitos, ou até mesmo dentro da engenharia de software quando você usa, por exemplo, uma forma mais formal de descrever uma especificação de requisitos, seja a partir de um modelo de casos de uso ou até mesmo a partir de um documento do processo Unificado chamado SRS (System Requirements Specification), especificação de requisitos de sistema, que normalmente tem centenas de páginas, que são auditadas e muitas vezes viram contrato para que os requisitos sejam congelados, para que você determine o escopo do produto a ser implementado por uma determinada empresa para que possa entregar o software para o seu cliente.

Mais uma vez, o SBOK, que é o Software Engineering Body of Knowledge, que é esse livro que delimita todas as áreas de conhecimento da engenharia de software, descreve também uma área chamada requisitos de software, que tem como um dos objetivos o desenvolvimento e a gestão dos requisitos de software dentro de todo o ciclo de vida de desenvolvimento. Lembre-se: a gente não está trabalhando com modelo de ciclo de vida em cascata, onde existe uma etapa inicial de documentação de requisitos que, enquanto você não termina essa etapa, você não vai para uma etapa subsequente. Na verdade, o que a experiência mostra pra gente é que requisitos de software são levantados e documentados durante todo o ciclo de vida do processo. Então você começa a levantar requisitos, você não espera terminar toda essa etapa para começar, por exemplo, a implementar. Então, à medida que você vai detalhando os requisitos e que o seu cliente vai priorizando esses requisitos, eles vão sendo implementados pelo time de desenvolvimento, software de valor vai sendo entregue no final de cada iteração, e dessa forma os requisitos vão evoluindo de forma interativa, incremental e sendo detalhados no momento oportuno.

Quando nós colocamos métodos, atividades, tarefas, ou seja, como a gente coloca alguma disciplina para levantamento e documentação de requisitos, nós temos uma área chamada engenharia de requisitos. Então, de maneira talvez mais formal, conforme descrito nos slides, o tema engenharia de requisitos é frequentemente usado para denotar a manipulação sistemática desses requisitos, ou seja, a coleta, documentação e atualização desses requisitos.

Conforme eu já antecipei um pouco, dentro da área de engenharia de software nós temos talvez duas vertentes muito utilizadas na prática: usar processos de desenvolvimento de software ou métodos ágeis para desenvolvimento de software. O processo de desenvolvimento de software mais famoso no mundo desde a década de 90 é o RUP, que é o Rational Unified Process, processo Unificado da Rational, que hoje é da IBM. A Rational é uma empresa que foi adquirida pela IBM ao longo dos anos. Dentro do processo Unificado, os requisitos em alto nível são elicitados, são documentados no começo do seu projeto numa fase normalmente chamada Inception. Lembrando que você tem quatro fases no processo Unificado: Inception, Elaboration, Construction e Transition. Dentro das fases de Inception e Elaboration é que a maior parte dos seus requisitos são levantados, mas lembrando também que é um processo que prescreve uma forma interativa e incremental, de forma que você vai detalhando requisitos ao longo do projeto, tendo em vista que nós não usamos modelo de ciclo de vida em cascata. Com RUP, de maneira similar nos métodos ágeis, embora seja talvez menos formal, tendo em vista que a principal técnica para levantamento e documentação de requisitos em métodos ágeis são as histórias de usuário. Mas lembrando que métodos ágeis também têm seus requisitos feitos de forma incremental e são detalhados apenas quando estão prestes a ser implementados pelo time de desenvolvimento. Contrastando com modelo de ciclo de vida em cascata, onde os requisitos são documentados na íntegra no início do projeto, em métodos ágeis nós priorizamos os requisitos junto com o cliente. A partir do momento que o cliente determinou a sua prioridade, aqueles requisitos que são detalhados para que sejam implementados dentro da próxima iteração de desenvolvimento. Aqueles requisitos que não são prioridade no momento não são detalhados no início de um método ágil. Essa talvez seja uma lição muito importante que os métodos ágeis trouxeram para toda a comunidade de desenvolvimento de software.

Então, eu vou trazer algumas definições do que é um requisito de software. Mais uma vez, um requisito é uma condição ou uma capacidade que um usuário precisa para resolver um problema ou para realizar um determinado objetivo. Se você olhar a segunda definição, também está associado com condição ou capacidade que deve estar presente no sistema ou um componente do sistema para satisfazer um usuário, contrato, um padrão ou algum outro documento que foi formalmente imposto, ou uma representação documentada de uma capacidade de acordo com as definições anteriores. Então, essas são definições clássicas de requisito: capacidade necessária por alguém ou que deve estar presente em um sistema ou um software em atendimento a esse alguém.

Uma coisa legal no SBOK é que essa definição de requisito é estendida para incluir também questões associadas com o projeto que desenvolve o software, que a gente chama de requisitos de projeto, que normalmente estão associados com tempo, com escopo e com custo. Mas eu vou apresentar isso com mais detalhes nos próximos slides. Então, de maneira básica, um requisito de software é uma propriedade, é uma capacidade que deve estar presente ou exibida em um sistema ou em um software para resolver um problema do mundo real.

Quando a gente fala requisitos do software, normalmente a gente classifica requisitos como funcionais ou não funcionais. Os requisitos funcionais, a grosso modo, você pode pensar que são os algoritmos que vocês implementam, são aquelas funcionalidades independente de tecnologia, aquilo que necessariamente deve ser feito. No sistema de matrícula, igual vocês trabalham na universidade, fazer matrícula é requisito funcional. Agora, se eu tô falando de qualidade, se eu tô falando de tecnologia, tô falando de requisito não funcional, que normalmente é subdividido em restrições tecnológicas ou qualidade de serviço. Se você está falando de qualidade do seu produto, também é requisito não funcional. Normalmente são aqueles advérbios que em inglês terminam com "ly": usabilidade, escalabilidade, manutenibilidade, ou seja, todos esses "adjetivos" da vida normalmente indicam requisitos não funcionais.

O próximo item presente na nossa estrutura analítica são os requisitos de projeto e requisitos do produto de software. Então, mais uma vez, essa é a referência utilizada pelo SBOK. Conforme eu disse para vocês, desenvolvedores são mais acostumados a definirem requisitos tecnológicos não funcionais, enquanto clientes e donos de negócio são melhores para descrever as regras de negócio, requisitos funcionais, embora isso não seja uma regra.

Um outro benefício é que, justamente conforme eu disse, a complexidade de requisitos é muito complexa, ela pode ser melhor gerenciada caso você separe em áreas, cada uma das áreas sendo atacadas pelo seu stakeholder que tem maior conhecimento naquela área em particular. Mais uma vez, engenheiros de software podem lidar com políticas, com complexidades de processo sem se preocupar com tecnologia, da mesma forma que o time de desenvolvimento às vezes se preocupa mais com tecnologia, deixando para que os clientes priorizem e detalhem as regras de negócio que devem ser implementadas.

E conforme eu disse, o paradigma de gestão "dividir para conquistar" ainda justificando o fato de você subdividir requisitos em áreas. Mais uma vez, de maneira talvez redundante, os stakeholders que não são engenheiros de software normalmente são especialistas no negócio, nos algoritmos, nas regras de negócio. Já os engenheiros de software, que não são esses stakeholders de negócio, são especialistas em tecnologia. Então, pessoas de negócio normalmente não entendem ou às vezes nem querem saber de tecnologia. Do outro prisma, muitas vezes quem é da computação, que é um programador, desenvolvedor, às vezes odeia justamente essa questão de querer entender o negócio e fazer documentação de requisitos em nível de negócio.

Existe uma analogia muito legal que ajuda a gente a diferenciar requisitos funcionais e não funcionais. Se você ainda tiver uma dúvida, talvez seja a analogia mais bacana, é chamada "filtro da tecnologia perfeita". A ideia é: imagina que você tem um supercomputador onde você não tem problema de memória, de processamento, de custo, ou seja, aquela máquina dos seus sonhos. Tudo aquilo que você ainda precisa especificar, sabendo que você tem uma máquina perfeita, é o que a gente chama de requisito funcional. Ou seja, eu posso ter a melhor máquina do mundo, com melhor performance, memória ilimitada, não tem problema de custo, nunca vai dar falha, mas se eu precisar fazer um software acadêmico, eu preciso ainda definir, por exemplo, que um aluno deve fazer matrícula, que uma matrícula não deve ser feita numa disciplina infringindo um pré-requisito. Observe que esses algoritmos, essas regras do negócio, elas são independentes da sua máquina, elas precisam ser especificadas mesmo que você tenha um hardware perfeito. Então, tudo aquilo que você precisa ainda especificar, que seja independente dessa máquina perfeita, são o que a gente chama de requisitos funcionais. A máquina perfeita com memória ilimitada, velocidade ilimitada, é um requisito não funcional.

Temos também a diferenciação entre requisitos de sistema e requisitos de software. Como já nós discutimos na aula passada a diferença entre sistema e software, imagino que isso aqui fique mais claro para vocês. Então, aqui são os livros que são utilizados pelo SBOK para entendimento desse item de decomposição analítica da área de conhecimento requisitos de software. Inclusive, o INCOSE, que é um conselho que rege as normas da engenharia de sistemas, define sistema como uma combinação de elementos que interagem de forma organizada para realizar um ou mais dos objetivos enunciados. Lembrando que sistemas incluem hardware, software, firmware, pessoas, informações, técnicas, etc., etc., etc. Ou seja, sistema engloba software, só que é muito mais do que software, e software é apenas uma parte de um sistema que é algo mais amplo. Então, existe alguns casos que é importante diferenciar entre requisitos de sistema e requisitos de software. No SWEBOK a gente tá trabalhando com requisitos de software, só que mais uma vez, os requisitos de software estão presentes num algo mais amplo que é o sistema. Por exemplo, um veículo autônomo: você tem parte dele que é software, mas você tem diversos outros componentes de um veículo autônomo que interagem entre si para a realização dos objetivos de um veículo. Ou, em outras palavras, os requisitos de software aplicam somente aos elementos de software dentro desse sistema maior, no caso, por exemplo, carro autônomo.

Entretanto, acredito que seja intuitivo que alguns requisitos de software podem ser derivados dos requisitos de sistema. É muito comum na indústria aeronáutica, a gente tem o termo "requisitos derivados". Essa é a referência utilizada nessa parte do SWEBOK. A ideia é que você tem vários níveis de requisitos e normalmente você tem stakeholders, aqueles clientes que estão no nível mais alto, digamos assim, estão um pouco mais distantes da implementação daquele requisito em determinado momento na engenharia, e nós temos aqueles requisitos que a princípio não trazem valor para esse cliente, às vezes ele não enxerga essa necessidade, mas eles são muito importantes para o projeto do sistema por conta da visão da engenharia. É o que a indústria aeronáutica e aeroespacial chama de requisitos derivados. Ou seja, um requisito derivado é o requisito que não foi feito por esse stakeholder externo em nível de negócio, mas ele foi imposto dentro do seu projeto pelo time de desenvolvimento porque o time de desenvolvimento sabe que aquele requisito é importante, por exemplo, para a arquitetura e para a estabilidade do seu sistema.

E por fim, nós temos as atividades de requisitos de software, que são várias. Porque quando a gente falar de requisitos de software, a gente tá falando de uma área muito ampla e que você também pode subdividir as atividades que são normalmente desempenhadas ao longo do ciclo de vida de desenvolvimento de software com relação a requisitos, começando desde a parte de desenvolvimento dos requisitos até a gestão dos seus requisitos. Então, como desenvolvimento de requisitos, nós vamos estudar tudo isso com mais detalhes depois. Nós temos basicamente as atividades de elicitação, análise, especificação e validação. Para quem não sabe, elicitação é aquela investigação inicial acerca dos requisitos, você ainda não detalhou, tá tendo aquele primeiro levantamento dos seus requisitos que devem estar presente no software a ser construído. A análise já é um pouco mais desse detalhamento. A especificação já é mais a documentação, de uma maneira mais formal, desses requisitos. E a validação é para você verificar se os requisitos realmente estão de acordo com a realidade, com a necessidade dos seus clientes.

Requisitos têm que ser gerenciados o tempo todo. Requisitos mudam o tempo todo, então você tem que ter um processo de controle de alterações de requisitos. Por exemplo, algumas atividades como scrubbing. Scrubbing, eu não sei em português, scrub é tipo você esfregar com uma escova assim, quando você vai lavar roupa, você esfrega. Scrubbing é essa atividade que você esfrega os requisitos para detalhar eles, deixar eles limpos, claros, concisos, de forma a dar qualidade naqueles requisitos. Mas você tem também atividade com relação ao que está dentro do sistema, o que está fora, associado com o escopo dos requisitos que devem ser documentados, inclusive controle de alterações de requisitos. Como requisitos vão mudar o tempo todo e o seu software atende os requisitos, quer dizer que o seu software vai mudar o tempo todo. Então você tem que ter um processo formal de controle de alteração de requisitos para que você possa, inclusive, manter rastreabilidade entre o que está implementado e aquilo que está definido nos seus requisitos.

Talvez uma forma de enxergar: o desenvolvimento de requisitos é você atingir um acordo sobre o que o software deve ser, deve fazer, o que deve ser construído. A gestão de requisitos é manter esse acordo ao longo do tempo do ciclo de vida de desenvolvimento de software.

A seguinte decomposição analítica da área de conhecimento requisitos de software é chamado elicitação de requisitos. O objetivo da atividade de elicitação de requisitos é você trazer à tona aqueles requisitos candidatos iniciais que deverão estar presentes no software que você tá produzindo. Também é chamado de captura de requisitos, descoberta de requisitos ou aquisição de requisitos, são outros nomes dados para essa atividade. É uma investigação inicial importantíssima acerca de requisitos de software que deverão ser especificados e depois implementados em bits e bytes dentro do projeto de desenvolvimento de software.

Lembrando que uma das questões bacanas que a atividade de requisitos, e elicitação de requisitos, traz para os responsáveis pela captura de requisitos é minimizar a incompletude de requisitos, que nós vimos como um dos grandes problemas da área de requisitos de software, tendo vista, conforme disse, que muitos dos problemas de requisitos não identificados. Talvez um dos sintomas é que você tenha feito uma elicitação inadequada dos requisitos que devem estar presentes no seu software. Mas claro, pessoal, como que você vai dar uma garantia que você conseguiu coletar todos os requisitos necessários para satisfazer o seu cliente, ou para que o seu software não produza erros e que, dessa forma, não cause danos aos stakeholders e cause acidentes provocando perdas inaceitáveis, como por exemplo danos ao meio ambiente, perdas humanas, perdas econômicas e assim sucessivamente? Não existe essa garantia. Embora não exista a garantia que você levantou todos os requisitos necessários, a atividade de elicitação, quando ela é bem executada, ela auxilia você justamente a minimizar esse problema de incompletude dos requisitos.

Então, detalhando um pouco mais essa área muito importante, essa atividade muito importante de elicitação de requisitos: de onde nós capturamos os requisitos? Mas talvez o mais importante é você identificar quais são as fontes. Então, talvez um tema que é muito usado e que talvez vocês, a partir de agora, vão ficar bem familiarizados, é o conceito de stakeholder. Stakeholder é qualquer pessoa, organização que tenha interesse alguma naquela fatia de negócio. Então, todas aquelas pessoas ou aqueles papéis que de certa forma, direta ou indiretamente, influenciam ou se beneficiam do software são chamados de stakeholders. Então, stakeholder é qualquer pessoa, qualquer grupo, qualquer organização que está envolvido no projeto, é afetado ou pode influenciar os resultados do projeto. Dessa forma, os stakeholders são uma das possíveis fontes de requisitos.

Exemplos de stakeholders: existem diversos: clientes, usuários, especialistas do negócio, as pessoas que vão trabalhar com a operação do seu software, alguns órgãos que norteiam, por exemplo, a área que você tá desenvolvendo aquele software, agências regulatórias. Caso não atenda essas regulamentações, essas empresas são fechadas por essas agências, ou às vezes muitas vezes multadas, e às vezes as multas são tão grandes que inviabilizam o negócio. Então, existem diversos stakeholders que têm um interesse ou que influenciam o desenvolvimento de software, e esses são fontes que vocês devem buscar para de certa forma elicitar os requisitos, inclusive os desenvolvedores, conforme nós dizemos, nós temos requisitos associados com qualidade e com restrições tecnológicas.

A Área de Conhecimento Requisitos de Software presente no SWEBOK (Parte 2/3)

Boa noite pessoal, dando continuidade aqui à discussão da área de conhecimento requisitos de software do Software Engineering Body of Knowledge, vamos discutir um pouco sobre análise de requisitos, requirements analysis. Essa estrutura analítica de decomposição de como a área de conhecimento requisito de software está sendo proposta na sua decomposição, vamos falar então um pouco de análise de requisitos e os seus subtópicos: análise de requisitos, a parte de qualidade de serviço, restrições, análise formal e também resolução de conflitos.

Mais uma vez, este é o livro usado como referência pelo SBOK para descrição dessa parte da área de conhecimento de requisitos de software chamada análise de requisitos. Lembrando que ontem nós discutimos que talvez uma das primeiras atividades para levantamento de requisitos é a elicitação de requisitos. Entretanto, a elicitação é apenas aquela atividade inicial para você levantar os requisitos que vão fazer do seu software um sucesso, que vão de certa forma entender o negócio para o qual você vai implementar uma solução em software. Uma vez elicitados os requisitos, nós precisamos detalhar, entender mais a fundo esses requisitos. Essa atividade é chamada análise de requisitos.

Então, começando aqui, vamos falar um pouco mais sobre questões básicas sobre análise de requisitos, que é esse item que eu chamei de 3.1, que também utiliza esse livro "Software Requirements" na terceira edição.

Basicamente, cada requisito que você identifica deveria não ser ambíguo, ou seja, uma vez que você coletou um requisito, ele elicitou um requisito, esse requisito deveria ser interpretado apenas de uma única maneira, de forma a não ter ambiguidade, porque requisitos ambíguos podem fazer com que seu time de desenvolvimento implemente soluções não adequadas para atendimento a esse requisito.

Uma outra característica: cada requisito que você levanta, que você documenta, deve ser testável de forma quantificável, justamente para que você possa verificar a compatibilidade daquilo que você implementou com aquilo que foi levantado pelo seu requisito.

O requisito também tem que ser, digamos assim, binding no sentido que ele tem que demonstrar algum valor para seu cliente. Ou em outras palavras, um requisito deve ser aquele que o seu cliente está disposto a pagar por ele e não está disposto a não ter ele na solução de software. Ou seja, o seu requisito tem que agregar valor para o seu cliente.

O requisito também, de maneira intuitiva, tem que realmente representar as necessidades dos stakeholders que dependem e que têm algum interesse naquele requisito. Também é muito importante que os requisitos usem o vocabulário dos stakeholders. Se você está capturando requisitos não técnicos, no sentido que você usou como fonte de captura desses requisitos analistas de negócio, especialistas de domínio, você tem que usar o vocabulário de negócio, vocabulário de domínio. Você não vai entrevistar, por exemplo, uma pessoa responsável pelo sistema acadêmico do ponto de vista do negócio da Universidade que não tem informação em computação e identificar requisitos com essa pessoa colocando na descrição que aquele requisito deve ser um lazy loading, tem que ser um singleton, tem que ser um facade, ou seja, começar a usar termos técnicos. Por quê? Porque isso não vai ao encontro das expectativas do seu usuário, da fonte de requisitos que você está entrevistando para a identificação desse requisito.

E de outra maneira, conforme eu disse ontem, existem várias partes interessadas na definição de requisitos, desde pessoas mais técnicas como pessoas não técnicas, como organizações, como usuários, clientes. Então, quando você identifica um requisito, é interessante que esse requisito passe pelo crivo de várias pessoas. Então, aquele requisito tem que ser compartilhado e tem que ser de certa forma verificável e aprovado por várias pessoas interessadas nos requisitos.

Estou falando dessas características de requisitos individuais. Quando você fala da coleção de requisitos que você obteve a partir de várias técnicas, seja através de surveys, seja a partir de entrevistas, seja analisando versões anteriores do seu software, seja avaliando softwares competitivos, seja avaliando normas ISO e IEC, ou seja, nós temos várias fontes de requisitos. Quando você captura todos esses e cria uma coleção de requisitos, existem algumas características também. Essa coleção teoricamente deveria ser completa, embora a gente não consiga garantir que toda a sua especificação de requisitos é completa. Não existe forma de você garantir que todos os requisitos foram levantados, mas existem várias técnicas que nós utilizamos que permitem de certa forma auxiliar nós, enquanto analistas de negócio ou pessoas que estão responsáveis por levantar os requisitos, a tornar aquela coleção de requisitos a mais completa possível.

Os requisitos também, essa coleção tem que ser consistentemente internamente, de forma que você não pode ter conflitos entre os requisitos. Tipo um requisito que fala para você fazer A e o outro requisito fala para você fazer não A. Um requisito conflitando com outro. Nós vamos ver que eliminação de conflitos é uma forma que nós temos de trabalhar e estar atento para evitar que aconteça, porque se você tiver conflito de requisitos, teoricamente você vai ter conflito durante a implementação do seu software e não vai conseguir atender de forma adequada as expectativas dos seus clientes.

Lembrando também que os requisitos têm que ser consistentes de forma externa. Você não pode ter conflitos entre os requisitos um com o outro ou requisitos que conflitam, por exemplo, com alguma legislação. Eu não posso determinar um requisito, levantar um requisito que infringe, por exemplo, uma norma do governo. Estou fazendo sei lá, um sistema, uma especificação de requisitos para um sistema elétrico, aí você tem a agência reguladora do governo que determina determinadas normas. Então, não posso determinar um requisito que vai de encontro, que conflita com requisitos determinados numa norma. Isso é importante também.

E claro, também acredito que seja intuitivo que os requisitos têm que ser viáveis, de forma que para a implementação daquele requisito você tenha uma solução que esteja dentro das restrições de orçamento, de custo, de qualidade e até mesmo da sua equipe. Então, não adianta você tentar coletar um requisito que o cliente acredita que vai dar valor para ele, mas esse requisito vai, por exemplo, esgotar praticamente todos os recursos financeiros do seu cliente. Ele mesmo não vai querer. Então, os requisitos também têm que ser viáveis. Talvez uma das formas que a gente tem para isso é quando você começa a quebrar os requisitos em requisitos menores e começa torná-los independentes um do outro, e talvez seu cliente priorize: "ó, eu não preciso disso tudo, mas essa parte dos requisitos talvez já me atenda, e ela me dá valor, e eu consigo pagar por ela, o time consegue desenvolver em tempo hábil e dentro de uma qualidade necessária e num escopo de projeto".

Apenas comentando aqui que às vezes um requisito que você identificou naquela atividade anterior, que é chamada elicitação de requisitos, talvez seja uma solução a ser implementada em vez de ser um problema real a ser resolvido. Então, quando isso acontece, você acaba tendo um risco de implementar uma solução que não seja a solução adequada. Então, nós temos que ter um pouco de cuidado com essa questão também para verificar se realmente os nossos requisitos são viáveis e estão de acordo com as expectativas e vão agregar valor para o meu cliente, de forma a não termos soluções que não sejam adequadas.

Existe até uma técnica que você pode usar que não é só para requisitos, é muito usado por exemplo na área de gestão de riscos, de análise de riscos. Na área de gestão de risco, você tenta identificar as causas de um risco. Talvez aí você tem uma técnica chamada "Five Whys". Basicamente, a técnica é você perguntar cinco vezes "por quê". Por que isso acontece? A pessoa responde, mas por quê? Para que você chegue, talvez, numa causa raiz. Então, talvez uma forma de você usar essa técnica para área de requisitos é você perguntar: por que esse requisito é necessário? A pessoa vai responder. Aí, com base naquela resposta, mas por quê? E dessa forma você vai perguntando cinco vezes. Normalmente, antes mesmo de chegar na quinta vez, você já tem uma resposta se aquele requisito é importante ou não para seu cliente. Porque basicamente, quando você vai parar de fazer a pergunta "por quê"? Quando você chegar naquela resposta, se você está perguntando "por quê" para o seu cliente e aquilo é importante, se ele responder assim: "ó, porque se isso não for feito, então o meu problema não vai ser resolvido". Se você chegou nessa resposta, quer dizer que aquele requisito é importante. Você tem que documentar e teoricamente você vai ter que trabalhar com ele de forma a ter uma solução ótima para atendimento a essa necessidade do seu cliente.

Então, conforme eu disse, raramente você precisa chegar em cinco porquês. Normalmente na segunda, terceira pergunta, o cliente já fala: "opa, se eu não tiver isso, eu vou perder alguma vantagem competitiva". Então, você vai chegar à conclusão que o requisito é importante e você vai documentar, esse requisito vai ser priorizado para você poder implementar.

Vamos falar um pouco da questão relacionada a restrições de qualidade de serviço. Existem alguns requisitos de especificação de requisitos que são baseados em critérios de aceitação. Isso aqui é muito comum, principalmente se você quiser transformar requisitos em casos de testes, ou vice-versa, para que você possa testar aquele requisito. Observe que essa especificação de requisitos baseada em critério de aceitação tem basicamente duas variações: o ATDD e o BDD. O ATDD é uma variação do TDD. Lembrando que o TDD, Test Driven Development, é aquela técnica do método ágil XP (Extreme Programming), criado pelo Kent Beck, que é um dos autores do Manifesto Ágil, em que se prescreve primeiro implementar um caso de teste, ver esse caso de teste falhar, aí sim ir para a implementação para passar nesse caso de teste, e depois refatorar sua solução. Isso é o TDD. O ATDD é uma variação do TDD, só que no nível mais alto. Em vez de você fazer um caso de teste, por exemplo, que vai demandar a implementação de um método, eu posso escrever um caso de teste, por exemplo, no contexto de uma história de usuário completa, para que meu teste de aceitação falhe e eu implemente a história do usuário até que esse teste de aceitação passe. Lembrando que basicamente nós temos vários níveis de testes automatizados. Nós temos os testes de unidade, que são aqueles testes que testam aqueles elementos de menor granularidade na sua solução, por exemplo, testa um método dentro de um objeto, dentro de uma classe. Nós temos os testes de integração, que são aqueles que testam a interação entre componentes do seu sistema, por exemplo, integração com banco de dados, integração com o sistema de arquivos, comunicação via rede, são testes típicos de integração. E temos os testes fim a fim, end to end, que também são chamados testes de aceitação, que são aqueles testes de caixa preta onde você testa o sistema de forma global como um todo.

E a outra variação que nós temos para essas especificações de requisitos baseadas em critério de aceitação é o que a gente chama de Behavior Driven Development, que é uma técnica para você justamente tentar guiar o desenvolvimento do seu software a partir de uma técnica também de testes automatizados, mas baseada numa sintaxe particular que chama Gherkin, que eu acredito que eu vou falar um pouco na sequência. Eu já adiantei aqui para vocês: o ATDD está dentro desse guarda-chuva chamado TDD, conforme discutimos. Lembrando que no caso do TDD, a ideia é que os casos de teste são implementados antes da sua solução. Repare que inverte a ordem natural: quando a gente aprende a programar, a gente programa e depois testa. TDD é ao contrário: você implementa o caso de teste e depois programa para passar naquele caso de teste. Dentro do TDD, você não pode incluir nenhum código novo sem ter antes criado um caso de teste que vai falhar. Somente quando você cria o caso de teste que vai falhar é que você parte para a implementação daquilo.

Então, o processo TDD ou ATDD basicamente tem três passos. Por exemplo, você pega uma história de usuário, que é uma especificação usando linguagem natural estruturada. Uma vez selecionada a história de usuário, você basicamente reúne os engenheiros de software, os especialistas de domínio, pessoal da área de teste, da garantia de qualidade. Essas pessoas, com base naquela história de usuário, entram num acordo de qual é o conjunto de casos de testes que devem passar, ou seja, que a solução deve atender para que você chegue à conclusão que aquela história de usuário foi implementada de forma correta. Então, antes mesmo de você partir para implementação, você define os casos de testes. Você tem que rodar o teste automatizado e vai falhar, barra vermelha. Esse é o indício: "opa, está no caminho". Aí você começa a fazer implementação até obter barra verde, quer dizer que o teste passou, a sua solução passou no teste. Após isso, normalmente você refatora a qualidade do seu código para continuar tendo barra verde.

Lembrando que essa questão de passar até você chegar na barra verde pode levar várias iterações de desenvolvimento ali para você chegar nisso, porque repare que estou falando em teste de aceitação, aquele teste mais amplo. Não estou testando um teste de unidade, um método específico de um objeto, estou testando a implementação, por exemplo, de uma história de usuário inteiro ou de um caso de uso inteiro. Então, às vezes eu preciso de várias sessões de desenvolvimento, vários dias de desenvolvimento, para conseguir chegar a uma barra verde. Após isso, você volta no passo um, pega uma nova história de usuário, novo caso de uso, reúne lá com o pessoal da garantia de qualidade, com os engenheiros de software, com especialistas de negócio, chega no consenso do conjunto de casos de teste que a sua solução tem que passar para atender aquela história de usuário ou aquele caso de uso, implementa esse caso de teste numa linguagem de programação que prescreve a escrita de casos de teste de forma automatizada, espera a barra vermelha, inicia implementação até obter barra verde, e assim de forma interativa e incremental.

Repare que essa minha escrita aqui no formato de caso de teste, só de eu mudar um pouquinho aqui, ela virou um requisito. Então, casos de teste e requisitos estão muito próximos uns dos outros. Apenas lembrando que um caso de teste de aceitação pode envolver N requisitos, ainda mais quando estamos falando de teste de aceitação, aquele teste mais amplo, fim a fim, que envolve uma série de implementações. Uma outra variação que nós temos, além do ATDD, é o BDD, que é um pouquinho mais estruturado porque ele usa uma linguagem natural estruturada chamada Gherkin, Gherkin syntax, sintaxe Gherkin. Inclusive, um dos últimos artigos que eu publiquei recentemente com dois alunos de TCC, eles trabalharam justamente com BDD. Eles criaram um método baseado em BDD para fazer avaliação, verificação de requisitos de software, mais especificamente para verificação de requisitos de segurança. Eles fizeram o TCC nisso, é o Vittor Rubatino e a Alice. Eles fizeram o TCC em dupla, escreveram no formato de artigo e nós submetemos para um evento em Las Vegas. Foi aceito e inclusive estou indo apresentar esse artigo agora em abril. Eles usaram essa técnica chamada BDD.

O legal do BDD é que você pode continuar descrevendo a sua funcionalidade como uma história de usuário. Uma vez que você definiu a sua história de usuário, você leva à criação de um cenário que vai ser aquele critério de aceitação para que a sua história de usuário seja aprovada, de forma que quando o time de desenvolvimento entregar a história de usuário para o cliente, o cliente vai ter capacidade de saber se o que foi entregue realmente corresponde àquilo que foi especificado nos casos de teste. Então, a sintaxe Gherkin são três palavrinhas: Given, When, Then. "Dado que", "quando", "então". Dado determinado contexto, quando há algum estímulo, acontece tal coisa.

A gente pega uma história de usuário. O verso da história de usuário normalmente é o critério de aceitação. Se você conseguir escrever esse critério de aceitação usando essa sintaxe Given-When-Then, que é chamada Gherkin, você de certa forma consegue automatizar isso usando algum framework de teste de aceitação com BDD. O Cucumber (pepino, em português) talvez seja o framework mais famoso para testes com BDD. Você escreve nessa linguagem natural estruturada chamada Gherkin syntax, aquilo vira teste automatizado que você vai rodar, vai dar barra vermelha, aí você vai começar a implementar até você conseguir passar e ter barra verde.

Só para vocês terem uma ideia de como funciona o BDD, imagine que eu tenho essa história de usuário: "Enquanto cliente de um banco, eu quero sacar dinheiro de um caixa rápido, de forma que eu possa ter o dinheiro sem ter que ir no banco". Repare que isso é uma história de usuário, linguagem natural estruturada, que tem: "qual o usuário?", o ator; "qual a ação dele?"; e "qual é o valor que é obtido a partir do momento que é realizado?". Você pode pegar o verso dessa história de usuário e escrever no formato de cenários usando sintaxe Gherkin. Repare como fica fácil. Um possível cenário: você vai ter N cenários, cada cenário vai ser um teste automatizado. "Dado que o saldo em conta é de $500, e o cartão do cliente do banco é válido, e o caixa eletrônico tem dinheiro suficiente dentro da sua gaveta de notas, quando o correntista solicita um saque de $100, então o caixa eletrônico deve liberar $100, e o saldo em conta deve ser $400, e o cartão do cliente deve ser retornado para ele." Observe que eu peguei essa história de usuário e criei um teste de aceitação para que, quando eu entregar essa história de usuário para o cliente, ele possa usar esse cenário.

Um outro cenário: "Dado que eu tenho um saldo de $50 na minha conta, meu cartão é válido, o caixa eletrônico tem dinheiro suficiente, quando eu tento sacar $100, o caixa eletrônico não deve liberar o dinheiro e deve informar que o saldo é insuficiente, o saldo deve continuar $50 (anterior a tentativa de saque), e o cartão deve ser retornado." Observe que para a mesma história de usuário eu já criei dois cenários. Qual é a vantagem desses cenários? Primeiro, que ele dá um entendimento claro do negócio. Segundo, que esse cenário, se você escreveu com essa sintaxe Given-When-Then, ela pode ser automatizada usando framework BDD, como por exemplo Cucumber. Então, o objetivo do BDD é ter uma lista completa (não completa, mas o maior número possível) de cenários de casos de teste para que você possa testar a solução de forma automatizada. A grande vantagem são testes automatizados. Ou seja, você vai clicar no botão, ele vai rodar todos aqueles testes para você e no final vai te dar um relatório se todos os testes passaram. Caso algum tenha falhado, vai te indicar uma barra vermelha e falar: "ó, aquele cenário particular está falhando", aí você vai ter que no seu código corrigir até passar.

Alguns cenários adicionais, por exemplo: quando o cliente tenta sacar com um cartão que é inválido, ou quando o cliente tenta sacar e não tem dinheiro dentro do caixa eletrônico. Às vezes acontece, imagina que aconteceu com vários de vocês já: às vezes você vai no caixa eletrônico, pede um valor lá, aí começa aí fica dois minutos, você fica até preocupado, e no final fala: "não tem dinheiro suficiente". Aí você até tira o extrato para ficar com medo de ter sido debitado na sua conta. A grande vantagem, eu acho, dos cenários BDD é que fica óbvio quais são os casos de teste. Então, você, no momento que você escreve a história de usuário e cria o critério de aceitação como cenários BDD, você já está escrevendo teste. Isso é muito legal na minha concepção, porque além de você já estar escrevendo os testes que vão garantir que aquela história de usuário foi implementada de forma correta, você já tem os casos de testes escritos numa sintaxe que você vai poder automatizar utilizando algum framework de Behavior Driven Development (BDD).

Com relação à ambiguidade, nós vimos que ambiguidade de requisitos é algo complexo, porque se você descreve um requisito ambíguo, quer dizer que o time de desenvolvimento pode ter mais de uma interpretação possível para aquele seu requisito e às vezes ele vai implementar uma das interpretações que não necessariamente é a implementação adequada para aquele requisito. Aí você vai acabar tendo bugs, vai acabar tendo erros naquela sua solução de software. Lembrando, no contexto da nossa disciplina, erros em software podem levar a falhas catastróficas que sejam de certa forma inaceitáveis do ponto de vista dos stakeholders, que vai gerar prejuízo financeiro, reputação para uma empresa, às vezes até morte de pessoas ou dano ao meio ambiente. Então, a gente tem que ter muito cuidado para que os nossos requisitos não sejam ambíguos. Até porque linguagem natural é ambígua, nós sabemos bem disso. Dependendo da palavra que nós falamos em português ou inglês, você tem mais de uma interpretação para aquela palavra. Então, a gente tem que ter um pouco de cuidado com essas questões. Quando você usa uma linguagem de casos de teste como BDD com sintaxe Gherkin, fica mais fácil resolver as ambiguidades por causa dos testes de aceitação.

Então, de maneira a finalizar um pouco essa discussão: quando você escreve o requisito em uma linguagem de casos de teste, usando uma especificação de requisitos baseada em critérios de aceitação, você acaba escrevendo requisitos que são muito mais precisos do que quando você usa linguagem natural não estruturada ou até mesmo estruturada, mas que não use uma especificação de requisitos baseada em critério de aceitação. Então, quando a gente combina, por exemplo, ATDD ou até mesmo BDD com outras áreas (a disciplina não é de teste de software), existem diversas técnicas de design de casos de teste que te dão dicas, diretrizes, técnicas para você especificar melhor os casos de teste. Quando você inclui essas técnicas juntamente com ATDD ou BDD, você reduz muita probabilidade de ter requisitos ambíguos e também de ter uma especificação de requisitos que não seja completa.

Existem diversas técnicas de design de casos de testes. Vocês basicamente já devem conhecer uma. Imagine que você está testando determinada faixa de valores. Normalmente, o que você faz? Você testa o menor valor, o maior valor, um valor fora da faixa menor, um valor maior acima da faixa, que são os limites que você está testando daquela faixa de valores. Por exemplo, se você tem algo do tipo "a nota deve ser de 1 a 10", normalmente você testa 0, 1, 10, 11, porque você está testando o limite. Isso é chamado boundary testing, justamente para tentar achar os erros. Existe várias técnicas para fazer design de casos de testes. Nós não temos uma disciplina de testes de software, mas é uma disciplina muito bacana que é uma área associada a qualidade de software, que permite você cada vez mais trabalhar com especificações e com implementações que atendam casos de testes bem projetados. Porque existe um mantra dentro da área de teste de software: é impossível testar tudo. Se é impossível testar tudo, você precisa de técnicas que permitam testar com menor esforço, usando uma técnica que vai permitir identificar o bug com o menor esforço possível, tendo visto que você não vai testar tudo. Uma dessas técnicas é: em vez de eu testar, imagine que você tem uma coisa que vai do limite de 1 a 100. Em vez de fazer o teste para 1, 2, 3, 4, 5 (repare que você não vai conseguir testar tudo, ou você vai gastar muito tempo), normalmente você vai testar para 0, para 1, talvez um valor no meio 50, 99, 100, 101. Ou seja, porque você sabe que o teste para 2, 3, 4 vai dar o mesmo resultado. Então, você não vai perder tempo. Como você não pode testar tudo, você tem que usar essas técnicas. Se alguém tiver interesse na área de design de testes, o livro muito famoso é do Copeland. Ele tem um livro muito legal de design de casos de testes. Nós temos também especificação de requisitos baseados em modelos. É uma outra forma que nós temos de documentar requisitos. Vocês estão acostumados, devem ter feito em algum momento diagrama de caso de uso. Diagrama de caso de uso é uma técnica visual, uma técnica de modelagem, uma ferramenta do UML para documentar requisito funcional. Você está usando uma linguagem, no caso UML, para uma notação gráfica para documentar requisito. Então, é uma possibilidade também, em vez de ficar usando apenas linguagem natural, seja ela estruturada ou não estruturada. Se você for da área de engenharia de sistemas, da mesma forma que nós temos o UML para área de engenharia de software, nós temos o SysML, que é essa notação gráfica para modelar sistemas da engenharia de sistemas. Ambas notações, UML e SysML, são da mesma organização OMG (Object Management Group), que é responsável por diversas outras especificações e notações gráficas além da UML e da SysML. Se você opta por documentar requisitos usando modelos com notações gráficas, só lembrando que a SysML possui dois tipos de modelos básicos, duas categorias: os modelos estruturais e os modelos comportamentais. No UML, por exemplo, um modelo de domínio em alto nível com diagrama de classes é um modelo estrutural. Um diagrama de sequência, que permite você enxergar colaboração de mensagens entre objetos que vão implementar a solução de software, é um modelo comportamental. Um caso de uso é um modelo comportamental, vai te dar o fluxo de interação do sistema com o ator ao longo do tempo. Então, vocês têm esses dois tipos de modelos quando você usa essas linguagens com notação gráfica para documentar requisitos.

Existe vários modelos estruturais não só no UML. Vocês devem ter visto em banco de dados modelo entidade-relacionamento. Diagramas entidade-relacionamento são uma forma de você documentar requisito de forma gráfica usando um modelo estrutural. O diagrama de classes é um outro exemplo que eu acabei de mostrar para vocês. Os modelos comportamentais também existem diversos no UML e na SysML. Você deve ter conhecido vários deles: caso de uso é um modelo comportamental; diagramas de interação, tipo diagrama de colaboração ou diagrama de sequência do UML; diagramas de atividade do UML são modelos comportamentais. Como que nós sabemos se um requisito possui uma boa qualidade? Existe alguns critérios, sim. Existe alguns atributos que podem nos auxiliar. Além de você ter essas instruções de requisitos, existe alguns atributos adicionais que normalmente nós incluímos numa especificação de requisitos de forma a estruturar melhor, dar mais consistência e tornar aquela especificação um pouco mais formal, embora ainda não estejamos falando de formalismo. Estou, digamos assim, semi-estruturando a especificação de requisitos. Normalmente, cada requisito você dá um identificador para ele. Essa tag é muito comum. Por exemplo, US-3458. Em vez de eu falar "enquanto aluno, eu quero fazer matrícula", você pode falar "US-3458". Às vezes você pode fornecer uma descrição, detalhes adicionais acima daquele requisito, uma explicação de por que aquele requisito é importante, quem foi a fonte que identificou aquele requisito, para qual ele vai agregar determinado valor, aquele requisito que você está descrevendo é funcional ou não funcional, ele depende de outros requisitos (depende da implementação de outros requisitos para que ele seja possível de ser implementado), ele tem conflito com algum outro requisito interno ou externo. Ou seja, existe uma série de alguns atributos adicionais que você pode colocar numa especificação de requisitos para estruturar um pouco melhor essa especificação. Então, em vez de ficar falando um por um aqui, talvez seja mais fácil você lembrar do formulário de caso de uso, onde você coloca um documento, uma tabela. Aí você coloca lá qual é o código do caso de uso, qual é o ator principal, qual é o pré-requisito, qual é o gatilho, qual é o cenário principal e quais são os cenários alternativos.

Para finalizar esta área de especificação de requisitos, nós temos que falar um pouco da questão de ser uma documentação de requisitos, uma especificação de requisitos incremental ou não. Basicamente, qualquer projeto que especifica explicitamente requisitos ou trabalha com especificação incremental ou com o que a gente chama de especificação compreensiva. Quando a gente trabalha com especificação incremental, cada versão dessa sua especificação de requisito contém apenas diferenças das versões anteriores. Ou seja, você tem uma versão base, aí você está fazendo uma especificação incremental que vai ter ou adições, ou alterações, ou remoções em cima dessa especificação base. Talvez uma vantagem dessa abordagem é que ela vai produzir um volume um pouquinho menor de especificações, porque você está especificando apenas as diferenças com base em especificações anteriores. Já a especificação de requisitos compreensiva: cada versão da sua especificação é completa. Você não incorpora apenas alterações, você cria uma nova versão completa de toda a especificação. Depende muito da cultura da empresa. Talvez a vantagem dessa abordagem é que você precisa de um documento só, que ele é completo, ele é compreensivo, ele é global. Então, um documento só é suficiente. No outro tipo de especificação, basicamente você vai ter várias diferenças entre as versões, entre o que foi acrescido, o que foi removido, o que foi alterado. Então, talvez seja mais difícil você acompanhar a evolução. Existe as duas formas de você fazer especificação de requisitos, e tem até o híbrido, que é o misto. É quando você faz umas coisas da versão X, versão 1.0, aí vai fazendo 1.1, 1.2, 1.3, 1.4. Repare que isso aí é você fazer especificação incremental a partir de uma versão básica 1.0. Aí chega um momento que você chega na 2.0, aí a 2.0 ela é completa, ela engloba tudo que estava na 1.0, 1.1, 1.2, 1.3, 1.4. Aí a partir da 2.0, você começa a fazer incremental e assim sucessivamente. Nesse sentido, quando você precisa de uma especificação, em vez de pegar toda a evolução, você pega, por exemplo, a 3.0, porque você sabe que ela é uma evolução que começou lá no 1.0, 1.1, 1.2, 1.3, 2.0, 2.1, até chegar a 3.0.
